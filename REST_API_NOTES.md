# REST API Design Notes — GymMonster

Doc 1 deliverable. This system's REST surface is much larger than food-ordering/furniture_store's (5 services × ~10 sub-domains) - depth here is calibrated accordingly: the critical, systemic security bug got a full fix across every instance found; everything else is documented with the pattern and severity, not individually rewritten across dozens of endpoints.

## CRITICAL, fixed: credentials transmitted as URL path segments

Confirmed and fixed **8 endpoints across `server-administrator` and `server-informations`** that took passwords - and in one case a full old/new username+password combination - as raw path segments: `PUT /clients/{username}/change-password/{oldPassword}/{newPassword}`, `DELETE /clients/{username}/deleteAccount` (reading a `{password}` path var), `PUT /classTrainers/{username}/password/{oldPassword}/{newPassword}`, `DELETE /classTrainers/{username}/delete/{password}`, `PUT /api/clients/{username}/{oldPassword}/{newPassword}/changePassword`, `PUT /api/clients/{username}/{newUsername}/{password}/changeUsername`, `DELETE /api/clients/{username}/{password}/deleteAccount`, `DELETE /api/pertrainers/AD/{username}/{password}/delete`, `PUT /api/pertrainers/AD/{username}/{newPassword}/{oldPassword}/updatePassword`, `PUT /api/pertrainers/AD/{oldUsername}/{newUsername}/{password}/updateUsername`.

Path segments end up in access logs, browser history, and `Referer` headers - this is one of the most well-known REST/API security anti-patterns (OWASP calls it out explicitly), and here it was live across 2 of the 5 services.

**Not a new pattern for this codebase**: `web-page`'s `RouterRegister` had already been fixed for the exact same issue (its own `RouterRegisterTest` documents why: *"credentials in the URL leak into browser history, access logs and Referer headers"*) - clearly from an earlier pass, but never propagated to `server-administrator`/`server-informations`, which had the identical anti-pattern. Every fix in this pass replicates that already-established, already-tested pattern: move the credential(s) into a small request-body record (`DtoChangePassword(oldPassword, newPassword)`, `DtoDeleteAccount(password)`, `DtoChangeUsername(newUsername, password)`), read via `request.bodyToMono(...)`.

**Also fixed in the same pass, found while tracing these routes**: `server-administrator`'s `ClientHandler.deleteClient` was reading `request.pathVariable("password")` from a route (`DELETE /api/admin/clients/{username}/deleteAccount`) that never actually declares a `{password}` segment - `pathVariable()` throws `IllegalArgumentException` when the name isn't in the matched pattern, so **every delete-client call on server-administrator was crashing**, not just leaking credentials. Same for `server-informations`'s `RoutersPreTrainer`, which had a second, dead route (`PUT /api/pertrainers/AD/{username}/{password}`) also pointed at `updateTrainerPassword` - that handler reads `newPassword`/`oldPassword`, which a 2-segment route never supplies either; removed as dead/broken rather than fixed, since the real route (now `PUT .../updatePassword`) already covers the same handler correctly.

**Not done this pass**: test coverage for the 4 newly-fixed router/handler pairs. `RouterRegisterTest` is the exact template to copy (`WebTestClient.bindToRouterFunction`, mock the service interface, assert the JSON body maps to the right service call) - recommend doing this immediately, it's a well-defined, low-risk addition now that the pattern exists in the codebase 4 times over.

## Systemic, documented (not rewritten): verbs in URLs

Nearly every mutation route across all 5 services encodes the action as a URL segment rather than relying on the HTTP method: `/deleteAccount`, `/change-password`, `/change-membership`, `/assignMembership`, `/dessignMembership`, `/updateBasicInformation`, `/assignSpecialty`, `/dessingSpecialty`, etc. This is Richardson Level 1 (resources exist, but verbs pollute the URL) across the board, not an isolated issue - the master prompt's own guidance is to migrate incrementally starting with the highest-traffic resource, and 5 services × ~10 sub-domains each is too large a surface to migrate blind in this pass. Flagging as the top structural finding for the next dedicated pass, starting with `clients` (the highest-traffic resource in both `server-administrator` and `server-informations`).

## Systemic, documented: error responses forward upstream bodies verbatim

`ClientHandler`'s (and the equivalent handlers in every service) generic `errorHandler` does `.bodyValue(errorResponse.getResponseBodyAsString())` for any non-404 `WebClientResponseException` - meaning if a downstream call fails, whatever that downstream service put in its error body (which could include stack traces or internal details, depending on what that service's own error handling does) gets forwarded straight to the end client verbatim. Combined with the ad hoc, inconsistent error shape (`{error, timestamp, status}` on 404s, `{error, timestamp}` - no `status` - on the generic fallback), this is the same class of issue as food-ordering-system's original exception leak, just via body-forwarding instead of `ex.getMessage()`. Recommend the same fix: a shared RFC 9457 `ProblemDetail`-based handler, applied once at the WebFlux `@ControllerAdvice`/`WebExceptionHandler` level so it's not reimplemented per-service.

## Not applicable / not evaluated this pass

Status codes (POST returning 200 instead of 201), pagination, idempotency keys: real findings almost certainly present here too (the same POST-returns-200 pattern seen in food-ordering/furniture_store shows up in every handler sampled), but auditing and fixing them individually across 5 services' full endpoint list is out of scope for this pass given the size of the critical fix above. Recommend as the next REST-review pass once the verb-in-URL migration above is planned, since fixing status codes on routes that are about to be renamed would be wasted work.
